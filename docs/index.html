Pokémon Gold & Silver: Space World 1997

A disassembly of the Gold and Silver prototypes shown at Nintendo Space World 1997 — reconstructed as human-readable RGBDS Game Boy assembly that reassembles into the original ROMs, byte for byte.

!

This is a preservation project, not a game in development. The whole point is that make reproduces the original prototype dumps exactly. Every source file is checked against the real bytes — so a change that shifts even one byte breaks the build. You are documenting a ROM, not editing one.

What you'll build

The four .asm object sources compile into eight ROM files — two games × normal/debug × raw/corrected-header — each verified against a known SHA1 in roms.sha1:

OutputOriginal nameWhat it is
pokegold-spaceworld.gbMONS2KN.COMGold, non-debug
pokesilver-spaceworld.gbMONS2SN.COMSilver, non-debug
pokegold-spaceworld-debug.gbMONS2KD.COMGold, with in-game debug menus
pokesilver-spaceworld-debug.gbMONS2SD.COMSilver, with debug menus

The -correctheader variants are the same ROMs re-patched with a valid cartridge header (the prototype's own header is malformed) so they run on real hardware and flashcarts.

Install the toolchain

Instructions target Apple Silicon Macs (M1–M4). The whole build runs natively — no Rosetta needed.

  1. Xcode Command Line Tools

    Gives you make, a C compiler, and git — everything the build harness and the in-repo C tools need.

    xcode-select --install
  2. Homebrew

    Package manager for the remaining dependencies. Skip if you already have it.

    /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
  3. RGBDS build dependencies

    RGBDS itself is compiled from source (next step); these are its build-time libraries.

    brew install bison libpng pkg-config
  4. RGBDS — pinned to v1.0.3

    RGBDS is the Game Boy assembler toolchain. This repo assembles only with the exact version in .rgbds-version. A newer release can produce different bytes and fail make compare, so build the tagged version rather than brew install rgbds.

    # Bison from Homebrew must win over the old system one
export PATH="$(brew --prefix bison)/bin:$PATH"

git clone https://github.com/gbdev/rgbds
cd rgbds
git checkout v1.0.3
make -j"$(sysctl -n hw.ncpu)"
sudo make install
cd ..
  5. Verify

    You should see 1.0.3. If you see anything else, that install will shadow the correct one on your PATH.

    rgbasm --version   # → rgbasm 1.0.3
▲

Version matters more than convenience. Homebrew's rgbds formula tracks the latest release. If you install it that way and the byte comparison later fails, a version mismatch is the first thing to suspect — check .rgbds-version against rgbasm --version.

Build the ROMs

From the repo root, one command builds all eight ROMs and checks them against the reference hashes.

# Build everything, in parallel, then verify SHA1s
make -j"$(sysctl -n hw.ncpu)"

A clean run ends with the SHA1 comparison passing silently. That green make compare is the definition of a correct build — there is no other test suite. If every line reads OK, your sources reproduce the original prototypes.

    brew install --cask sameboy

  3. Load symbols for debugging

BGB via CrossOver / Wine

BGB is Windows software but is the reference debugger for GB assembly work. On Apple Silicon it runs through a translation layer:

# One option: Wine (CrossOver is the paid, more polished route)

▲

Emulator vs. real hardware. For an emulator, load the plain *.gb. For a flashcart or real Game Boy, use the *-correctheader.gb build — the prototype's original header is invalid and real hardware may reject it.

The debug builds

The -debug.gb ROMs expose the developers' original in-game debug menus — field, fight, sound, monster, and subgame menus (see engine/debug/). They're the fastest way to jump around content the prototype can't otherwise reach.

The Language

RGBDS & the SM83 CPU

This codebase is written for the Game Boy's 8-bit CPU using the RGBDS toolchain. If assembly is new to you, this page gives you the mental model; the next page is the syntax reference.

The processor: Sharp SM83

The Game Boy runs a Sharp SM83 core (often labelled LR35902) — a close relative of the Zilog Z80 / Intel 8080. It's an 8-bit CPU: it works on one byte at a time, has a tiny set of registers, and no notion of functions, loops, or variables. You write the individual steps.

  • Registers are the workspace. Eight 8-bit registers — a b c d e f h l — that can pair up into 16-bit registers af bc de hl. a (the accumulator) is where arithmetic happens; hl is the usual pointer.
  • Memory is addressed, not named. A "variable" is just a labelled address in RAM. [hl] means "the byte in memory that hl points at."
  • Flags drive branches. An operation sets flags (zero, carry…); the next instruction can jump based on them. That's how if and loops are built.

The toolchain: RGBDS

RGBDS is four programs. The Makefile orchestrates them so you rarely call them by hand, but knowing the pipeline explains what each file type is for:

ToolTurnsInto
rgbasm.asm source.o object files
rgblink.o files + layout.linka raw .gb ROM (+ .sym/.map)
rgbfixa raw .gba ROM with a patched header + checksum
rgbgfx.png images.2bpp/.1bpp Game Boy tile data

Banking: why main.asm is a list

The cartridge is bigger than the CPU's address space, so ROM is split into 16 KB banks that get swapped into view one at a time. ROM0 (the home/ code) is always visible; the numbered ROMX banks are paged in as needed. Because a routine in one bank can't directly call one in another, the codebase uses helper macros:

  • farcall — call a routine in another bank and return.
  • predef — call a routine by an index from a pointer table (data/predef_pointers.asm), used for common cross-bank helpers.

Repo Anatomy

The build system

Four hand-written top-level .asm files, a linker script, and a force-included prelude — that's the whole skeleton. Everything else is INCLUDEd into one of them.

The five roots

Each of these becomes one object file per ROM variant (see the ROM_OBJ list in the Makefile):

FileBecomesHolds
home.asmROM0 (always mapped)Core routines callable from anywhere: vblank, interrupts, text, menus, map/overworld, farcall/predef dispatch
main.asmThe numbered ROMX banksThe master INCLUDE list — it decides which engine/data file lives in which bank
audio.asmAudio banksThe sound engine + music/SFX/cry data
maps.asmMap banksAll the map data
ram.asm(no ROM bytes)RAM address declarations only — VRAM/WRAM/SRAM/HRAM layout

layout.link — where banks go

rgblink needs to know the physical bank of every SECTION. layout.link is that map. When you need to know which bank a piece of code ends up in, main.asm (section names) plus layout.link (section → bank) is the answer.

includes.asm — the global prelude

This file pulls in the charmap, every macro, and every constants file. The Makefile passes it via rgbasm -P includes.asm, which force-includes it at the top of every translation unit. That's why any file can use any constant or macro without importing it.

# from the Makefile
RGBASMFLAGS += -Q8 -P includes.asm

The prime directive: don't move bytes

▲

Reordering data, "tidying" a table, or changing a constant's value can shift the output and break make compare. After any edit, rebuild and confirm the SHA1 check still passes. Renaming labels and adding comments is always safe; changing emitted bytes is not.

Continuous integration

GitHub Actions (.github/workflows/main.yml) builds with DEBUG=1 on both Ubuntu and macOS, runs make compare, then .github/checkdiff.sh — which fails the build if anything in the working tree changed (e.g. a stray regenerated file). On the upstream pret repo it also pushes fresh symbol files to the symbols branch.

Repo Anatomy

home/ & main.asm

The always-available core, plus the index that lays out everything else.

home/ → ROM0

Bank 0 is permanently mapped into the CPU's view, so routines here are callable from any other bank without banking tricks. It holds the low-level plumbing the whole game leans on. A sampling from home.asm's include list:

  • System: rst.asm, interrupts.asm, vblank.asm, init.asm, serial.asm, joypad.asm
  • Graphics & text: text.asm, vcopy.asm, window.asm, menu.asm, pic.asm, fade.asm
  • World: map.asm, overworld.asm, map_objects.asm, movement.asm, tileset.asm
  • Cross-bank dispatch: farcall.asm, predef.asm — the machinery behind the farcall/predef macros

main.asm → the ROMX banks

This file is almost pure structure: a series of SECTION "bankN", ROMX blocks, each listing the engine and data files that belong in that bank. It's the table of contents for the bulk of the game and the fastest way to answer "where does feature X live, and in which bank?"

SECTION "Battle Core", ROMX
    INCLUDE "engine/battle/core.asm"
    INCLUDE "engine/overworld/wildmons.asm"
    INCLUDE "engine/battle/start_battle.asm"
i

Banks are packed to fit real hardware limits. If you add code to a bank that's already full, the link step fails — that's main.asm and layout.link telling you to place it elsewhere.

ram/

Not code and not data — just names for memory addresses. These declarations are what let the rest of the source say wPartyCount instead of a bare hex address.

Repo Anatomy

garbage/

Leftover and padding bytes from the original ROMs, preserved verbatim. It looks like junk because it is junk — but it has to be byte-exact.

Real cartridge ROMs contain filler between sections, abandoned data, and uninitialised regions that happened to hold whatever was in the developers' build. To reproduce the prototype's exact SHA1, that content is captured here rather than cleaned up or zeroed out.

▲

Don't "fix" it. Deleting, compacting, or reformatting anything in garbage/ will change the ROM and break make compare. Its messiness is the point — it's faithful preservation, not a mistake to tidy.

Curious findings buried in here (recognisable graphics, unused data) are exactly the kind of thing the pret #prototypes-and-leaks community documents.

The World

The Story of Nihon

The prototype is set in Nihon (ニホン — literally "Japan"), the region later rebuilt into Johto for retail Gold & Silver. This page reads it on three levels: the attract-mode demo you could actually play at the Space World '97 booth, the fuller Story Mode the developers left half-coded and normally unreachable in the ROM, and a speculative reading of where that unfinished story was heading.

i

Quotations and symbols here are taken straight from this repository — the map scripts under maps/, the sprite and trainer tables, and the reconstructed text glossary. §2 describes content that is normally inaccessible (see its patch note). §3 is clearly-marked speculation, not established canon.

§1 The Space World '97 demo

What the cartridge boots into — the build shown on the floor — is not the story. It is a short, self-contained loop meant to prove a Gold & Silver existed and let a passer-by hold new Pokémon in the palm of a Game Boy. So it skips every ceremony: no name entry, no professor, no gift scene. You simply begin as a Trainer who already has a Pokémon in hand, standing in a finished-looking town.

The polished interiors, the mail from "Oak," the missing-professor radio bulletin, the lab scene — none of that is part of this playable loop. It exists in the ROM, but you reach it only through the Story Mode below.

§2 The unfinished Story Mode

Buried in the same ROM is the game's real opening — a proper new-game sequence the demo build never lets you reach. The Cutting Room Floor documents how to force it: patch ROM offset 0x5585 from 0x8D to 0xB9, and the cartridge boots the story instead of the attract loop. It is genuinely raw — the change destabilises overworld movement in many emulators and tends to crash — and only the introduction, up to the first rival battle, is fully coded and playable. What follows is that intro, told from the scripts, NPCs and Pokémon that actually run.

Where the code runs out

Having taken whichever starter beats yours, the rival wants an immediate battle — and this is the exact point the finished world ends. His party isn't stored the way this build's battle engine expects. §3 If Nihon had never become Johto — speculation

!

From here on is an informed extrapolation, not documented canon. It braids together fragments that sit unused in the ROM — a second "evil" Oak, a phantom bird, a time machine, two rival evil teams — into the story the prototype seems to have been reaching for.

The loose ends still in the ROM

None of the following is reachable in play, but all of it is concrete — sitting in maps, sprite tables and dialogue the developers wrote and then abandoned. Together the fragments sketch a far larger plot than the intro ever delivers:

  • A missing professor — and a second Oak. A radio bulletin (unreachable in play) reports that "Professor Oak has vanished from Kanto," yet you meet him in Silent Hill. The sprite table holds two Oaks: SPRITE_OKIDO, the professor you meet, and SPRITE_EVIL_OKIDO — an impostor, for whom a whole map (maps/HighTechImposterOakHouse.asm) was built in the distant High-Tech city.
  • A phantom Pokémon. A letter on the lab PC, from Oak's assistant, hunts a legendary the assistant now doubts is real: "that certain Pokémon you asked me to find… Maybe that thing really is a fictitious Pokémon after all." The obvious candidate is newcomer #247 Hōō (Ho-Oh), a fit for Old City's sealed Five-Story Pagoda.
  • A Time Machine. Pokémon-Center NPCs keep describing a device that can "even trade Pokémon across time" — the ancestor of retail's Time Capsule — but never let you touch it.
  • New types on display. The build is mid-invention: it carries a prototype Bird type and a Metal type (later Steel), and shows off the first Dark-type like an exhibit — "This is Houndoom. A type of Pokémon there's never been before." Behind it sit 100 newcomers (#152–251), barely half of which reached retail intact — see the newcomers list.
  • Two evil teams, and a whole region. Trainer classes exist for both the proto Geruge-dan and a returning Team Rocket. The landmark table names fifteen-plus cities — Silent Hill, Old City, West, High-Tech, Font, Birdon, Newtype, Sugar, Stand, Prince, North, South — with Kanto folded in as a single city (Silph Co., a Game Corner, a wink-to-camera "Game Freak HQ"), nearly every town carrying its own gym.

Picture Nihon left intact: a pocket-sized Japan whose towns are named for ideas rather than plants — Silent, Old, High-Tech, Newtype, Stand — with the whole of Kanto shrunk to one nostalgic city you can walk back into. It is one year after a boy from Pallet finished the first Pokédex, and the world is convulsing with new life: unfamiliar species everywhere, and rumours of new types entirely.

The lure

Two children in Silent Hill — you, and Oak's grandson next door — receive the same unsigned letter: "there is something I simply must give you." It reads like an honour. In this version it is bait. Someone needs a fresh generation of trainers scattered across Nihon, dutifully logging every new Pokémon into networked Pokédexes — because that census is the fastest way to triangulate one specific creature: the phantom the real Oak vanished chasing, the rainbow bird Ho-Oh, roosting atop Old City's sealed Five-Story Pagoda.

The two Oaks

The Oak who greets you in Silent Hill is genuine but frail — "a worn-out old man," by his own admission, running out of time. The Oak in High-Tech city is not Oak at all: SPRITE_EVIL_OKIDO, a double who has stolen the most trusted name in the Pokémon world and, with it, command of the region's research apparatus. The radio's careful phrasing — "vanished from Kanto… or caught up in some incident" — is the impostor's cover story doing its work. Every Pokédex the children fill in feeds his map, not the professor's.

The emotional charge is that the rival is Oak's grandson. Retail Gold & Silver replaced him with Silver, Giovanni's son — a stranger to the professor. Here, the boy racing you to catch legendaries is chasing, without knowing it, the thing wearing his own grandfather's face. His arc bends from "I'll be the greatest trainer" toward a confrontation no eleven-year-old should have to have.

The assistant, the teams, the machine

The assistant who keeps promising "we'll meet again" is the pivot — the one insider who realises the Oak giving orders from High-Tech is fake, and who has been quietly steering you toward the truth. The muscle splits cleanly: the Geruge-dan are the impostor's private organisation, built to seize the pagoda and the phantom; the resurgent Team Rocket are the old guard from Kanto, Giovanni's remnants, chasing the same prize for their own ends. Nihon becomes a three-way scramble — you, the false Oak's Geruge-dan, and Rocket.

The Time Machine in Old City is the keystone. If Pokémon can be traded across time, then so, perhaps, can information — a way to reach back to the Kanto of Red and Blue, where the real Oak's reputation was forged, and to prove which professor is the true one. The climax writes itself: Ho-Oh atop the pagoda, the Time Machine humming below, the impostor and the genuine Oak in the same frame, and the grandson forced to choose who to believe.

How it all resolves — and where the pieces actually went

Nihon's finale would have been a march through the League buildings of every city — proto leaders named for mushrooms and toads giving way to the Kanto-carried Elite Four (Lorelei, Bruno, Lance) — while the professor mystery paid off at the pagoda. Game Freak never shipped that. When Nihon was rebuilt into Johto, its threads were cut apart and redistributed:

Prototype threadWhere it surfaced in retail

Read that way, the prototype isn't a lesser Gold & Silver — it's a different one, a moodier detective story about a stolen identity and a phantom bird, quietly disassembled and rebuilt into the adventure the world actually got.

History

Origins & History of the Disassembly

This repository is a fork of pret/pokegold-spaceworld, a community effort that began the day the prototype cartridges were dumped and — over more than eight years — turned a raw, anonymous ROM into fully readable, fully labelled assembly. This page reconstructs that journey from the commit history of every branch.

i

Everything below is drawn from the project's own git log — first commit 2018-05-27, most recent work 2026-08, spanning 820 commits from 38 contributors across the master, en, patch, and symbols branches.

§1 Where it came from

In May 1997, at Nintendo Space World, playable Gold & Silver prototypes were shown on the show floor — a world called Nihon, dozens of Pokémon that never shipped, and a story only half-written. Those cartridges then vanished for two decades. In May 2018 the demo carts were finally dumped and the ROM images released to the public.

Within days, Sanqui spun up a disassembly on a self-hosted Gitea server (git.sanqui.net:3000/pret/pokegold-spaceworld) — the earliest merge commits still point back to it. The first README is a single blunt line: "WIP disassembly of the Spaceworld 1997 Gold proto." The goal was the same one that defines every pret project: not to describe the ROM but to reproduce it byte-for-byte from human-readable source. The project soon moved to GitHub under the pret organisation, where it has lived since.

The method is reverse-engineering by reconstruction. You start with an opaque binary and a build that reassembles to exactly those bytes; then, one region at a time, you replace raw hex with named labels, macros, and comments — never changing the output, only your understanding of it. Early commits lean heavily on macros and constants imported wholesale from the sister projects pokered and pokecrystal, giving the anonymous prototype a vocabulary borrowed from its better-understood retail descendants.

§2 From ROM dump to documented code

The arc below traces that transformation — from a nameless binary to source in which every byte has a meaning.

May 2018 · the dump

Two demo cartridges become public ROMs

The Space World '97 Gold & Silver prototypes are dumped and released. A raw binary baserom with a known checksum is the only starting point — no symbols, no source, just bytes.

May–Jul 2018 · bootstrap

A build that reproduces the ROM

Sanqui, ISSOtm, Rangi, Tauwasser and others stand up the RGBDS project: a Makefile that reassembles to the original bytes, a "shim" symbol generator, and constants/macros ported from pokered and pokecrystal. home.asm is split out; the checksum comparison becomes the definition of "correct."

2018 · bank by bank

Dumping the code banks

Pokeglitch and others work through the ROM bank by bank ("began dumping bank 1"… "Finished dumping bank 1"), converting hard-coded pointers into labels and extracting the first graphics and text. This is the raw, laborious middle of a disassembly.

2019–2021 · the systems

Maps, audio, graphics & menus take shape

Steady, distributed work identifies whole subsystems: map data and scripts, the SGB border and palette packets, the audio engine with cries and sound effects, the Pikachu minigame, and the in-game debug menus. Travis CI is swapped for GitHub Actions; both the Gold and Silver debug ROMs build.

2022–2024 · keeping the lights on

A quiet maintenance stretch

Activity slows to a trickle — mostly commits that keep the project building against newer RGBDS releases ("make it actually build with current RGBDS") plus partial dumps of the last stubborn banks. The disassembly is far along but not finished; large regions remain unnamed.

2025 · the revival

The last banks fall

A burst of renewed effort labels and splits off the remaining banks one after another — bank 01, 03, 05, 09, 0B, 0D, 0E, 14, 23 — decompiles every battle animation, and finishes the Pokédex and sprite-animation objects. The build is upgraded to RGBDS 1.0.

Jun–Aug 2026 · naming the last symbol

100% documented

A tool, tools/unnamed.py, is added with a webhook that reports the percentage of symbols still auto-named — turning "finish the disassembly" into a number to drive to zero. Every remaining RAM and ROM symbol is named, all leftover garbage/ data is extracted, and on 2 Aug 2026 the webhook is removed with the note "now that 100% of symbols are named."

Label all unnamed symbols (#184) · Finish extracting garbage (#182)

§3 What "finished" means here

Reaching 100% named symbols is a real milestone: there is no longer any anonymous sub_XXXX or byte_XXXX in the source. Every routine, table, and RAM address has a human-chosen name, the graphics live as real PNGs, and even the padding and leftover junk in the original ROMs is accounted for in garbage/. As documentation, the disassembly is complete — you can read this prototype the way you'd read the retail games.

!

"Finished" means the ROM is fully understood and reproduced — not that the game is finished. The prototype itself is still a half-built 1997 demo: the Story Mode is only coded up to the first rival battle, and much of the region is placeholder. The disassembly documents exactly that unfinished state, faithfully.

§4 What a completed disassembly unlocks

A byte-perfect, fully-labelled disassembly is a foundation, not a dead end. Because the source now reads like ordinary code, it becomes a launchpad for work the raw ROM could never support:

ResearchPreservation & studyA permanent, human-readable record of a lost build — how 1997 Game Boy code was structured, and how features evolved on the way to retail Gold & Silver. ModdingRom hacks & restorationsNamed labels make it feasible to fork the source and change it deliberately — restore cut Pokémon, re-enable dummied content, or build an original hack on the prototype's engine. CompletionFinishing the lost gameThe unfinished Story Mode could be coded forward past the first rival battle — turning the demo into the fuller adventure the scripts and maps only hint at. ReferenceComparative disassemblyDiff against pokered/pokecrystal to trace exactly which routines survived, mutated, or were cut between the prototype and the shipped games.
!

One caveat before you hack. This repository's own contract is byte-for-byte reproduction — make compare must still match the original dumps. Any change that alters the output bytes intentionally (a restoration, a new feature) belongs on a fork with its own goals, not on master. The completed disassembly is the clean base you branch from.

Beyond the Repo

The symbols branch & gb-asm-tools

The README's two "See also" links point outside your working tree. Here's what each is and how it connects back to this codebase.

branch The symbols branch

Link: pret/pokegold-spaceworld @ symbols. This is an orphan branch in the same repository that holds generated .sym and .map files — not source code.

  • A .sym file maps every ROM address to its label name; a .map file describes the final bank layout.
  • CI regenerates them on every push to master and commits the fresh copies to the symbols branch (see the "Update symbols" step in the workflow).
  • They're kept on a separate branch precisely because they're build artifacts — master stays source-only, and .sym/.map are in .gitignore there.

How it ties in: load a .sym into an emulator debugger (SameBoy, BGB) and addresses become readable label names, so you can set breakpoints on DelayFrame instead of a hex address. You can generate your own locally with make DEBUG=1 — the symbols branch just saves you the build, and matches the exact upstream bytes.

i

On a personal fork, the CI steps that push to symbols are gated to github.repository_owner == 'pret', so they won't run for you. Use make DEBUG=1 to produce symbols yourself.

repo gb-asm-tools

Link: pret/gb-asm-tools. A separate, shared repository of general-purpose utilities used across all of pret's Game Boy disassemblies — not required to build this project.
